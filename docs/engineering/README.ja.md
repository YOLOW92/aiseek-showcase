# 技術設計：採用技術よりも設計判断

[← ポートフォリオ](../../README.ja.md) · [English](README.md) · [中文](README.zh-CN.md) · [技術事例](CASES.ja.md)

AiSeek P0–P72 は実際に本番運用された製品であり、インストール可能なオープンソース一式ではありません。中核ソースは非公開です。次の図は**ゲーム開発前の概念的な構成**であり、AiSeek 2.0 の最新構成ではありません。

![独自制作のアーキテクチャ図](../../assets/architecture.svg)

> 独自制作の説明図です。画面キャプチャや外部監査の結果ではありません。

## 主な技術境界

| 領域 | 当時の構成 | 守るべき規則 |
|:--|:--|:--|
| Web | React 19、React Router SSR、Tailwind、TypeScript、Motion | 描画経路から直接モデル・DBを呼ばない |
| API | Node 24、Fastify、Zod | 権限・プランをサーバー側で検証 |
| 非同期処理 | pg-boss、LangGraph.js、SSE | 長時間処理とリクエスト描画を分離 |
| 文書処理 | Python、FastAPI、Crawl4AI、Doclingなど | 取得の可否と公開権限を別に評価 |
| データ正本 | PostgreSQL 17、pgvector、PGroonga、Apache AGE | 関係テーブルが正本、グラフ投影は再生成可能 |
| 運用 | Docker Compose、VPS CI、リバースプロキシ、バックアップ | 秘密情報、リリース、マイグレーションを管理 |

目的はサービス数を増やすことではなく、責務を分離することです。技術のバージョンは各段階で変化しており、10月6日の古い一覧をP72の最終構成として扱いません。

## 重要な設計判断

**1 · 根拠の分類はモデルの自信ではなく規則。** FACT / SUPPORTED / HYPOTHESIS を決定する条件を定義。[実装例](../../proof/code/promote.ts)。

**2 · 関係の種類を固定。** エンティティの組合せ、逆関係、時間的制約を登録し、モデルによる無制限な追加を防ぐ。[実装例](../../proof/code/relation-registry.ts)。

**3 · 日中英の検索をそれぞれ設計。** PGroongaによる日中文全文検索、名称の統合、英語向けの検索処理を使い分ける。

**4 · 配信元の異常を世界の変化と混同しない。** 完全な日単位の比較、履歴基準、収集元の変化を反映。高度な検出器の長期比較は未完了。

**5 · 限られた計算資源の待ち行列を制御。** モデル予算と代替経路を管理し、計算待ちには上限を設ける。[実装例](../../proof/code/gate.py)。

## セキュリティと制約

- 情報取得の許可と、取得内容を再公開する権利は別に評価します。
- 私的なResearchは認証、所有者確認、該当データの行レベル保護で守ります。
- アーキテクチャテストで層とモデルルーターを検証します。
- DB変更は前方専用のマイグレーションを用います。
- P72でブラウザーのエラー報告機能を追加。P72で試されたリリース前ブラウザースモークテストは**後に削除**されたため、現行機能とは記載しません。
- 出典と分類の仕組みがあっても誤りは残り、精度を述べる場合には評価条件が必要です。
