# AiSeek 背后的三个判断

[作品集](../README.zh-CN.md) · [English](CASES.md) · [日本語](CASES.ja.md) · [证据](../proof/README.zh-CN.md)

## 01 / 让信息真正有用

**问题。** 信息流可以越堆越多，却没有让读者理解更多。文章、主张和已经核验的变化是不同的东西；混在一起，会让网站显得忙碌，却把理解的工作留给读者。

**我的判断。** 我把信息产品的中心放在变化上：发生了什么、为什么重要、有什么支撑、接下来观察什么。Research 成为辅助能力，访客不需要先理解研究体系才能用网站。我要求事实、有依据的推断和假设在展示上可区分，并能追到支撑它们的原文段落。

**交付结果。** 主站把变化、背景档案、证据段落、结构视图与持续阅读连接起来，提供三种语言。方法说明和更正记录让读者有地方了解证据如何处理，也能质疑已经发布的内容。

**真实取舍。** 质量检查也可能误拦有用的信息。公开更新记录记载过一次过严的复核规则，使头条停在旧内容上。后来对它进行了修正。这个过程比声称核验永远不会失败更有价值：及时性和可信度需要平衡，有争议的内容需要复核路径。

**体现的能力。** 产品定位、信息架构、验收标准，以及在决策伤害阅读体验时修正它的判断力。

**查看：**[方法说明](https://aiseek.dev/zh/method)、[更正记录](https://aiseek.dev/zh/corrections)、[更新日志](https://aiseek.dev/zh/changelog)。这些材料支持对产品行为的描述，不是事实准确率的评测。

## 02 / 让边界可以被检查

**问题。** 同时拥有公开阅读、私有研究和外部服务的系统，不能只在文档里承诺边界。错误的依赖可能暴露私有工作，让页面等待外部调用，或者把付费权限留在浏览器里判断。

**我的判断。** 我把这些分隔写成明确的工程约束：前端读 API，长任务异步执行，权限在服务端校验，外部调用经过受控入口。标准记录和可重建视图各负其责。我要求检查能在项目扩展时发现边界违规。

**选取的实现证据：**

| 片段 | 能说明什么 | 不能证明什么 |
|---|---|---|
| [服务端权限检查](../proof/code/server-entitlements.ts) | 请求的研究深度被限制在账户权益范围内。 | 所有授权路径都正确。 |
| [单次任务预算检查](../proof/code/run-budget.ts) | 新增预计用量与任务上限进行比较。 | 已测得的成本下降，或所有外部调用均已审计。 |
| [前端依赖检查](../proof/code/frontend-boundary.test.ts) | 架构测试拒绝前端直接依赖后端服务。 | 完整的安全审计。 |

这些是核验过的私有版本中的简短原样片段，用来展示通用防御性工程，不公开核心产品机制。[来源清单](../proof/source-manifest.json)。

**真实取舍。** 明确的契约和异步任务比一个请求包办所有工作需要更多协调，也让权限、失败处理和工作检查有清晰落点。这是责任划分的选择，并不意味着复杂性消失了。

**体现的能力。** 架构判断、服务端控制、资源意识，以及把要求变成可审阅检查的能力。

## 03 / 上线后继续对产品负责

**问题。** 功能能跑只是独立产品的一部分。读者还需要看得懂的语言、能用的手机体验、回来的理由、报告错误的途径，以及连接其他工具的稳定入口。

**我的判断。** 我把中文、英文和日文当作完整的产品界面；把关注、提醒和简报放进回访流程；让更正和联系可访问；提供带账户额度的只读集成入口。更新日志面向读者描述变化。

**交付结果。** 更新记录包含多语言检索改进、手机体验调整、订阅、邮件简报、浏览器推送和 API/MCP。产品公开提供状态、方法、归属说明与更正记录。主站是查看这些体验的入口。

**真实取舍。** 界面越多，需要保持主张含义和权限一致的地方越多。翻译完标签并不代表本地化已经完成。我把产品承诺限定在实际交付范围内，测量结论只在证据足够时使用。

**体现的能力。** 完整交付、多语言产品思考、运营责任，以及对上线后读者体验的持续关注。
